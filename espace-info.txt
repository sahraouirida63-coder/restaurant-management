Name        : Restaurant Management System (RestaurantPOS)
Type        : Full-stack Web Application (SPA + REST API)
Purpose     : Digitise all operations of a restaurant — order taking, kitchen
              management, cashier billing, stock control, and delivery tracking
              — through a single unified platform with seven role-specific
              dashboards.

The system is designed to be deployed locally using XAMPP (Apache + MySQL) for
the PHP backend and Node.js/Vite for the React SPA. The two halves communicate
exclusively over HTTP/JSON using Bearer token authentication.

  Browser  (React 19 SPA — http://localhost:5173)
      │
      │  HTTP/JSON  ·  Authorization: Bearer <token>
      ▼
  Laravel 12 REST API  (http://127.0.0.1:8000/api)
      │
      ▼
  MySQL 8.x Database  (database: "restaurant")

- The frontend and backend are entirely decoupled. The React SPA never renders
  server-side HTML; all pages are client-side routes.
- Authentication is stateless: Laravel Sanctum issues a personal access token
  on login. The token is stored in localStorage and attached to every outgoing
  Axios request via a request interceptor.
- CORS is handled by a custom CorsMiddleware that whitelists localhost:5173,
  127.0.0.1:5173, localhost:3000 and 127.0.0.1:3000 plus ports 8000.

──────────────────────────────────────────────────────────────
  POST   /logout             → Revoke current token        [all roles]

  DELETE /employees/{id}     → Delete Employee + User account   [manager, owner]

  GET    /menu               → List menu items (with image_url) [all]
  GET    /menu/{id}          → Get single menu item             [all]
  POST   /menu               → Create menu item (multipart OK)  [manager, owner, chef]
  PUT    /menu/{id}          → Update menu item                 [manager, owner, chef]
  DELETE /menu/{id}          → Delete menu item + image file    [manager, owner, chef]

  GET    /stock              → List stock + low-stock alerts    [stock, manager, owner]
  POST   /stock              → Add stock entry                  [stock, manager, owner]
  PUT    /stock/{id}         → Update stock quantity            [stock, manager, owner]

  GET    /deliveries         → List deliveries (eager: order)   [delivery, manager, owner]
  PUT    /deliveries/{id}    → Update delivery status           [delivery, manager, owner]

NOTE: The frontend api.ts also calls PATCH /deliveries/{id}/status but the
      backend only registers PUT (apiResource). This is a minor discrepancy —
      PUT works because apiResource maps the update() method to PUT.

8. AUTHENTICATION & SECURITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Login Flow
   POST /login → AuthController::login()
   - Validates email (string) and password (min 4 chars)
   - Looks up User by email, verifies password with Hash::check()
   - Creates a Sanctum personal access token ("API Token")
   - Returns { user: { id, name, email, role, phone, status }, token }

2. Token Storage (Frontend)
   - Token saved in localStorage under key "token"
   - User object saved in localStorage under key "user"
   - On app start, AuthContext validates the stored token by calling GET /user
   - If validation fails, localStorage is cleared → redirect to /login

3. Request Interceptor (api.ts)
   - Every outgoing Axios request automatically includes:
     Authorization: Bearer <token from localStorage>

4. Response Interceptor (api.ts)
   - 401 responses from /login or /user endpoints clear localStorage and
     redirect to /login (auto-logout on token expiry)

5. Backend Middleware Stack (api.php)
   - auth:sanctum  → Sanctum token verification for all protected routes
   - role:X,Y      → RoleMiddleware checks user.role is in the allowed list
   - CorsMiddleware → Applies CORS headers; whitelists local dev origins

6. Frontend Guard (ProtectedRoute.tsx)
   - Checks isAuthenticated; redirects to /login if false
   - Checks user.role against the allowed roles[] prop; redirects if mismatch
   - Shows LoadingSpinner while token validation is in progress

7. CORS Configuration
   Allowed origins: localhost:5173, 127.0.0.1:5173, localhost:3000,
                    127.0.0.1:3000, localhost:8000, 127.0.0.1:8000

11. KEY PATTERNS & NOTABLE DESIGN DECISIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Dual-Record Pattern (Employee ↔ User)
──────────────────────────────────────
  Creating an employee (EmployeeController::store) simultaneously creates:
    • A User record  → used for login / authentication (HasApiTokens)
    • An Employee record → used for HR data (phone, profile_image)
  Deletion of an employee cascades to the User record (matched by email).
  This avoids polymorphism but creates a denormalised dual-record structure.

Table Resolution Logic (OrderController::store)
─────────────────────────────────────────────────
  The frontend sends either table_number (1-20 label) or table_id (which can
  also be a number label). The backend first tries to resolve by table.number,
  then falls back to table primary key. This handles the frontend sending the
  display number rather than a database ID.

Short-Polling Notification System
──────────────────────────────────
  Two separate polling loops run every 8 seconds:
    1. Layout.tsx — drives the top-bar bell badge (global, for all roles)
    2. WaiterDashboard.tsx — drives the per-waiter notification dropdown and
       green table dots. Tracks previously seen order IDs (useRef) to detect
       newly-ready orders and auto-show the notification panel.
  This is a simple polling solution; no WebSockets or SSE are used.

Image Handling (MenuController / EmployeeController)
─────────────────────────────────────────────────────
  Images are stored in Laravel's public disk under storage/app/public/menu/.
  The storage:link command creates public/storage → storage/app/public symlink.
  resolveImageUrl() returns either the full URL (if already a http URL) or
  asset('storage/' + path) for locally stored files. Old images are deleted
  from disk when a menu item is updated or deleted.

Singleton API Client
─────────────────────
  api.ts exports a single instance `apiClient = new APIClient()`. The class
  configures an Axios instance with base URL + interceptors once at startup.
  All pages import this singleton rather than creating their own Axios instances.

Role-Aware Sidebar
───────────────────
  Layout.tsx defines a static `roles` map keyed by role name. Each entry lists
  the navigation items for that role. The sidebar only shows links relevant to
  the logged-in user's role, and applies a unique accent colour per role
  (yellow=owner, blue=manager, green=waiter, orange=chef, purple=cashier,
   cyan=stock, pink=delivery).

getDashboardStats() Returns Static Mock Data
─────────────────────────────────────────────
  The Owner Dashboard calls apiClient.getDashboardStats(), but this method
  currently returns hardcoded values (revenue: 45231.89, orders: 2350, etc.)
  without making any API call. Charts also use static weekly data arrays.
  These would need to be replaced with real API endpoints for production use.

12. OBSERVATIONS, POTENTIAL ISSUES & MISSING PIECES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Issues / Limitations
──────────────────────
1. HARDCODED API URL
   src/services/api.ts defines `const API_BASE_URL = "http://127.0.0.1:8000/api"`.
   The .env file defines VITE_API_URL but it is never used. This means the
   frontend cannot be reconfigured for staging/production without editing source.

2. MOCK DASHBOARD STATS
   getDashboardStats() returns static mock data. The Owner dashboard shows
   fictional numbers. No real API endpoint exists for aggregated stats.

3. PATCH vs PUT for Deliveries
   Frontend calls PATCH /deliveries/{id}/status but the backend registers
   PUT via apiResource. PATCH is not registered, so this call would return 405
   (Method Not Allowed). In practice the call would need to use PUT or the
   route needs to be fixed.
   UPDATE: apiClient.updateDeliveryStatus uses PATCH, but the route file only
   has `apiResource('deliveries', ...)->only(['index','update'])` which maps to
   PUT. This is a real bug that would prevent delivery status updates from the
   frontend.

4. DUAL-RECORD DENORMALISATION
   Employees and Users maintain separate records linked only by email address.
   If an employee's email is updated, the User record is NOT updated in sync
   (EmployeeController::update does not touch the users table).

5. PASSWORD DOUBLE-HASH RISK
   Employee::store passes the plain-text password to both User::create (which
   uses the User model's setPasswordAttribute mutator to hash it) AND to
   Employee::create (which hashes via its boot() method). This is correct for
   distinct records, but any code that passes an already-hashed password could
   result in a double-hash.

6. STOCK THRESHOLD HARDCODED
   The low-stock alert in StockController uses `quantity < 10` hardcoded.
   The `reorder_level` column exists in the stock table but is not used for
   the alert comparison.

7. NO REAL-TIME UPDATES
   All "live" updates rely on polling every 8 seconds. If the server or network
   has latency, order status changes can be delayed by up to 8 seconds on all
   clients. WebSockets (Laravel Echo / Pusher) or SSE would provide true
   real-time updates.

8. NO PAGINATION
   All list endpoints (orders, menu, employees, stock, deliveries) return all
   records without pagination. For restaurants with large datasets this could
   become slow.

9. NO AUTOMATED TESTS FOR FRONTEND
   No Vitest/Jest test files exist in the React project. The backend has a
   PHPUnit setup (phpunit.xml + tests/ directory) but no custom test files
   were found beyond the Laravel defaults.

10. LEFTOVER .new FILES
    src/App.tsx.new and src/index.css.new exist in the React src directory.
    These appear to be draft/backup files that were never cleaned up.

11. APP.TSX.NEW / INDEX.CSS.NEW
    These files shadow the main source files and should be removed or renamed
    to avoid confusion.

12. NO PAYMENT PROCESSING
    The `payments` table and Payment model exist, but no PaymentController or
    API route is registered. The Cashier dashboard marks orders as "paid" by
    updating the order status, not by creating a payment record.

13. RESERVATIONS NOT SURFACED IN API
    The Reservation model and seeder exist, but there is no ReservationController
    or API route. The Manager dashboard mentions "Reservations" as a tab but
    it would need an API endpoint to function properly.

Positive Patterns
──────────────────
+ Clean separation between frontend and backend
+ Consistent dark design system with a single brand color
+ Role-based access enforced on both frontend (ProtectedRoute) and backend
  (RoleMiddleware) — defence in depth
+ Image upload with old-image cleanup on update/delete
+ Singleton API client with automatic token injection and 401 auto-logout
+ Framer Motion animations throughout for a premium UX feel
+ Responsive layout: collapsible desktop sidebar + mobile drawer with overlay
+ OrderController::store validates items against the database and ignores the
  client-sent waiter_id (derives it from the authenticated user instead —
  prevents privilege escalation)
+ UserSeeder uses updateOrCreate (idempotent — safe to re-run)
